## 2026-01-18 - US-020: Fix sm upgrade for repos cloned before universal git support

- What was implemented:
  - Added `resolve_repo_cache_path()` function in `paths.rs` that checks both new-style and legacy cache paths
  - Added `legacy_github_cache_path()` helper function for backward compatibility
  - Updated `upgrade_with_lock()` in `repo.rs` to use `resolve_repo_cache_path()` instead of `repo_cache_path()`
  - Updated `pin()` in `repo.rs` to use `resolve_repo_cache_path()` as well

- Files changed:
  - src/paths.rs - Added resolve_repo_cache_path(), legacy_github_cache_path(), and 4 tests
  - src/commands/repo.rs - Updated upgrade_with_lock() and pin() to use resolve_repo_cache_path()

- **Learnings for future iterations:**
  - Before universal git support, GitHub repos were cached at `git/{owner}/{repo}` (legacy path)
  - After universal git support, repos are cached at `git/{host}/{owner}/{repo}` (new path)
  - When accessing existing repos (upgrade, pin), use `resolve_repo_cache_path()` which checks both paths
  - For new clones, use `repo_cache_path()` which always returns the new-style path
  - Only GitHub repos have legacy paths - other git sources (GitLab, local) don't need this handling

  - When stripping prefixes leaves a relative-looking path, check if it matches common root dirs before treating as relative
  - Tests should cover both correct format (file:///) and lenient format (file://) variations
